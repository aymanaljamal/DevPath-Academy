Enterprise React Project Structure

Introduction

As React applications grow, organizing files becomes just as important as writing good code.

A small project with only a few pages can keep everything inside the src folder without any structure.

Example:

src
│
├── App.tsx
├── Login.tsx
├── Customer.tsx
├── Order.tsx
├── Employee.tsx
└── index.css

This works for very small applications.

However, an enterprise application may contain:

  • 100+ pages
  • 500+ React components
  • Hundreds of API endpoints
  • Multiple development teams
  • Thousands of files

Without a proper architecture, maintaining the project becomes nearly impossible.

For this reason, professional companies organize React applications into specialized folders where each folder has one responsibility.

Why Project Structure Matters

A good project structure provides:

  • Better maintainability
  • Easier onboarding for new developers
  • Better scalability
  • Less duplicated code
  • Easier debugging
  • Cleaner architecture
  • Separation of concerns
  • Reusable code

Every developer on the team immediately knows where each file belongs.

How Data Flows Through the Application

Before understanding the folders, you should understand how data travels inside a React application.

Imagine a user clicks the Create Customer button.

The request flows like this:

User → Customer Page → Customer Form Component → Customer Service → Customer API → Axios Instance → Spring Boot REST API → Controller → Service → Repository → Database

Database → Repository → Service → Controller → JSON Response → Axios → Customer API → Customer Service → React Query → React Component → User Interface

Understanding this flow makes understanding the folder structure much easier.

Root Project Structure

A typical enterprise React application may look like this:

src
│
├── api
├── assets
├── components
├── config
├── constants
├── context
├── hooks
├── layouts
├── pages
├── providers
├── routes
├── services
├── store
├── types
├── utils
├── validations
├── features
├── shared
│
├── App.tsx
├── main.tsx
├── index.css
└── vite-env.d.ts

Each folder has a single responsibility.

api/

Purpose

The api folder contains all communication with the backend.

Its responsibility is only sending HTTP requests.

It should never contain business logic.

Example:

api
│
├── api.ts
├── auth.api.ts
├── customer.api.ts
├── employee.api.ts
├── order.api.ts
├── payment.api.ts
└── report.api.ts

Example:

export function getCustomers() {
    return api.get("/customers");
}

Responsibilities:

  • GET requests
  • POST requests
  • PUT requests
  • DELETE requests
  • Upload requests
  • Download requests

Not responsible for:

  • Filtering data
  • Business rules
  • UI logic

assets/

Stores static resources.

Example:

assets
│
├── images
├── icons
├── fonts
├── videos
└── styles

Contains:

  • Logos
  • Images
  • Icons
  • Fonts
  • Global CSS
  • Animations

components/

Contains reusable UI components.

Instead of rewriting the same button 50 times:

<button>Create</button>

You create:

<Button />

Project:

components
│
├── common
├── forms
├── layout
└── ui

Examples:

  • Button
  • Card
  • Modal
  • Table
  • Loader
  • Input
  • Pagination

Reusable everywhere.

pages/

A page represents an entire screen.

Examples:

pages
│
├── Dashboard
├── Customers
├── Orders
├── Employees
├── Reports
└── Login

Usually every page corresponds to one route.

Example:

/customers

loads

CustomersPage.tsx

layouts/

Layouts define page structure.

Example:

  • Dashboard Layout
  • +--------------------------------+
  • Navbar
  • Sidebar | Main Content
  • Footer
  • +--------------------------------+

Instead of rewriting Navbar and Sidebar on every page, pages are wrapped inside layouts.

hooks/

Contains reusable custom hooks.

Example:

hooks
│
├── useAuth.ts
├── usePagination.ts
├── useApi.ts
├── useTheme.ts
└── useToast.ts

Hooks encapsulate reusable logic.

Example:

const { login } = useAuth();

services/

Contains business logic.

Services sit between Components and APIs.

Flow:

Component → Service → API

Example:

API returns:

100 customers

Service filters:

Only Active Customers

Components receive clean data.

routes/

Responsible for navigation.

Example:

routes
│
├── AppRouter.tsx
├── ProtectedRoute.tsx
├── PublicRoute.tsx
└── RouteGuard.tsx

Responsibilities:

  • Page navigation
  • Authentication protection
  • Authorization
  • Lazy loading

context/

Stores global application state.

Example:

AuthContext → Current User → Accessible by every component

Examples:

  • Authentication
  • Theme
  • Language

store/

Contains centralized state management.

Usually used with:

  • Redux Toolkit
  • Zustand
  • MobX

Stores application-wide data.

providers/

Wrap global providers around the application.

Example:

<QueryClientProvider>

<AuthProvider>

<ThemeProvider>

<App />

</ThemeProvider>

</AuthProvider>

</QueryClientProvider>

constants/

Stores values that rarely change.

Example:

  • API_URL
  • ADMIN_ROLE
  • CUSTOMER_ROLE
  • ORDER_PENDING
  • ORDER_COMPLETED
  • MAX_UPLOAD_SIZE

Instead of repeating strings throughout the project.

config/

Contains project configuration.

Examples:

  • Axios
  • React Query
  • Theme
  • Environment
  • Application Settings

utils/

General helper functions.

Examples:

  • formatDate()
  • formatCurrency()
  • downloadFile()
  • parseJwt()
  • generateUUID()
  • capitalize()

Pure functions.

No React code.

types/

Contains TypeScript definitions.

Example:

export interface Customer {

    id: number;

    name: string;

    phone: string;

}

Used everywhere.

validations/

Contains validation schemas.

Usually built using:

  • Zod
  • Yup

Example:

CustomerSchema

Rules:

  • Name required
  • Phone format
  • Email validation

features/

Some enterprise projects organize by feature.

Example:

features
│
├── auth
├── customer
├── employee
├── order
└── payment

Each feature contains:

customer
│
├── api
├── components
├── hooks
├── pages
├── services
├── types
└── validations

Everything related to Customers stays together.

shared/

Contains code shared across multiple features.

Example:

shared
│
├── components
├── hooks
├── utils
├── constants
└── types

Main Files

main.tsx

Application entry point.

Responsibilities:

  • Mount React
  • Create root
  • Register providers
  • Render App

App.tsx

Root application component.

Responsibilities:

  • Render layouts
  • Render router
  • Global application structure

index.css

Global CSS styles.

Typically imports:

  • Tailwind
  • Variables
  • Global styles
  • Fonts

vite-env.d.ts

TypeScript declarations generated for Vite.

Allows TypeScript to understand:

import.meta.env

File Extensions

.ts

TypeScript file.

Contains:

  • Functions
  • Classes
  • Utilities
  • Services
  • APIs
  • Hooks (without JSX)

Example:

customer.service.ts

.tsx

TypeScript + JSX.

Contains React Components.

Example:

CustomerTable.tsx

.css

Regular CSS file.

Global styles.

.module.css

Scoped CSS.

Styles only affect one component.

Example:

import styles from "./Button.module.css";

.scss

Sass stylesheet.

Supports:

  • Variables
  • Nesting
  • Mixins

.svg

Vector graphics.

Best for:

  • Icons
  • Logos

.png

Raster image.

Supports transparency.

.jpg

Compressed photograph.

Best for photos.

.json

Configuration or data.

Examples:

  • package.json
  • tsconfig.json
  • launch.json

.env

Environment variables.

Example:

VITE_API_URL=http://localhost:8080

Never commit secrets.

.env.local

Local environment variables.

Ignored by Git.

.md

Markdown documentation.

Used for:

  • README
  • Documentation
  • Architecture
  • Tutorials

Summary

A well-designed React project structure is not about creating many folders—it is about assigning a clear responsibility to each part of the application.

When every folder has one purpose, developers can quickly locate files, understand data flow, collaborate efficiently, and scale the application without creating technical debt.

This architecture is the foundation of professional React applications used in enterprise environments.
