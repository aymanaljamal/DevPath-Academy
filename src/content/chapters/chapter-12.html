Understanding Data Flow in React Applications

Introduction

One of the biggest challenges for new React developers is understanding how data moves through an application.

Many beginners understand Components, Hooks, or APIs individually, but they don't understand how everything connects together.

In enterprise applications, every button click follows a predictable journey.

Understanding this journey is the key to reading any React project.

This chapter explains that journey from the moment a user interacts with the application until the data reaches the database and returns back to the screen.

The Complete Data Flow

Imagine the following scenario.

A user opens the application and clicks:

Create Customer

The request travels through multiple layers.

User → React Page → React Component → Event Handler → Custom Hook (Optional) → Business Service → API Layer → Axios → Internet (HTTP Request) → Spring Boot Controller → Spring Boot Service → Repository → Database

Database → Repository → Service → Controller → JSON Response → Axios → API Layer → Service Layer → React Query → React Component → Browser UI

Every enterprise React application follows approximately this architecture.

Step 1 — The User

Everything starts with the user.

The user can:

  • Click a button
  • Fill a form
  • Type into an input
  • Select an item
  • Delete data
  • Update data
  • Navigate to another page

Example:

<Button>Create Customer</Button>

Nothing happens until the user performs an action.

Step 2 — React Page

The current page receives the interaction.

Example:

CustomersPage.tsx

Responsibilities:

  • Display data
  • Organize components
  • Connect UI with business logic

Example:

export default function CustomersPage() {

    return (

        <CustomerTable />

    );

}

Pages usually contain multiple components.

Step 3 — React Component

Components contain the actual UI.

Example:

CustomerForm.tsx

Responsibilities:

  • Render HTML
  • Receive Props
  • Display State
  • Handle Events

Example:

<Button onClick={handleSubmit}>

Create

</Button>

The component itself should remain as simple as possible.

Step 4 — Event Handler

When the button is clicked:

onClick={handleSubmit}

React executes:

function handleSubmit() {

    ...

}

This function becomes the starting point of the business process.

Step 5 — Reading State

Before sending anything to the server, React reads the current data.

Example:

const [customer, setCustomer] = useState(...)

Current values:

  • Name
  • Phone
  • Address
  • Email

These values become the request body.

Step 6 — Validation

Professional applications validate data before sending it.

Example:

  • Name required
  • Phone format
  • Email format
  • Password length

Libraries:

  • Zod
  • Yup
  • React Hook Form

If validation fails:

  • Stop
  • Show Error
  • Do NOT call API

Step 7 — Custom Hooks (Optional)

Many enterprise projects move logic into hooks.

Example:

  • useCustomer()
  • useOrders()
  • useEmployees()

Instead of writing everything inside the component.

Example:

const { createCustomer } = useCustomer();

Now the component becomes much cleaner.

Step 8 — Business Service

The Service Layer contains business rules.

Example:

customer.service.ts

Responsibilities:

  • Prepare data
  • Transform data
  • Filter data
  • Decide which API to call
  • Handle business logic

Example:

Component → Customer Service → Customer API

Services should not render UI.

Step 9 — API Layer

Now the request reaches:

customer.api.ts

Responsibilities:

  • Send HTTP Requests
  • Receive HTTP Responses

Example:

export function createCustomer(data){

    return api.post("/customers", data);

}

Notice:

No validation.

No filtering.

No UI.

Only communication.

Step 10 — Axios

Every API file usually uses one shared Axios instance.

Example:

const api = axios.create({

    baseURL: "http://localhost:8080"

});

Axios automatically:

  • Adds Base URL
  • Adds Authorization Token
  • Converts JSON
  • Handles Errors
  • Executes Interceptors

Step 11 — HTTP Request

Axios converts the JavaScript object into JSON.

Example:

{

"name":"John",

"phone":"123456"

}

Then sends:

  • POST
  • /customers

Through the Internet.

Step 12 — Spring Boot Controller

The request reaches:

CustomerController

Responsibilities:

  • Receive Request
  • Validate Request
  • Call Service

Example:

@PostMapping

public Customer create(...)

Controllers should remain thin.

Step 13 — Spring Service

Now business logic executes.

Example:

CustomerService

Responsibilities:

  • Validate business rules
  • Calculate values
  • Execute workflow
  • Call Repository

Step 14 — Repository

Repository communicates with the database.

Example:

CustomerRepository

Responsibilities:

  • Save
  • Update
  • Delete
  • Find

Example:

repository.save(customer);

Step 15 — Database

Finally data reaches:

  • MySQL
  • PostgreSQL
  • Oracle
  • SQL Server

The record is stored.

The Response Journey

Everything now returns backwards.

Database → Repository → Service → Controller → JSON → Axios → API → Service → React Query → Component → Screen

React Query

Most enterprise applications use React Query.

Responsibilities:

  • Cache Data
  • Loading State
  • Error State
  • Refetch
  • Synchronization

Instead of:

  • Loading...
  • Loading...
  • Loading...

React Query handles it automatically.

Updating the UI

React receives new data.

State changes.

React re-renders only affected components.

Example:

  • Old Table
  • 10 Customers
  • ↓
  • New Table
  • 11 Customers

Only the table updates.

The entire page is NOT reloaded.

Why React Re-renders

React compares:

Old Virtual DOM → New Virtual DOM → Diff Algorithm → Only Changed Nodes → Real DOM Update

This makes React very fast.

Complete Enterprise Example

Imagine the Laundry Management System.

Customer submits a new laundry order.

User → OrdersPage → CreateOrderForm → handleSubmit() → React Hook Form → Zod Validation → useOrder() → order.service.ts → order.api.ts → Axios → POST /orders → Spring Boot → OrderController → OrderService → OrderRepository → MySQL

MySQL → OrderRepository → OrderService → OrderController → 201 Created → Axios → React Query Cache Update → Order Table → Success Toast → UI Updated

This is exactly how enterprise React applications operate.

Error Flow

Suppose something fails.

Example:

Database Down

The flow becomes:

Database → Exception → Spring Boot → HTTP 500 → Axios → Interceptor → API Layer → Service Layer → React Query → Component → Toast → Error Message

The user sees:

  • Unable to create customer.
  • Please try again.

Instead of a broken application.

Authentication Flow

Login follows a slightly different path.

User → Login Form → Validation → auth.service.ts → auth.api.ts → POST /login → Spring Boot → JWT Token → Axios → Local Storage → Auth Context → Protected Routes → Dashboard

Every future request automatically includes:

  • Authorization:
  • Bearer

Axios Interceptors usually attach this token automatically.

File Upload Flow

Uploading files introduces another path.

User → Select File → File Object → FormData → Axios → Multipart Request → Spring Boot → Storage Service → Cloud / Local Disk → Database stores file path → Response → React → Image Preview

Data Flow Responsibilities

Layer Responsibility
User Starts the interaction
Page Organizes UI
Component Displays interface
Event Handler Responds to user actions
Hook Reusable logic
Validation Validate inputs
Service Business logic
API HTTP communication
Axios Network client
Spring Controller Receives request
Spring Service Business processing
Repository Database communication
Database Stores information
React Query Cache & synchronization
React Component Displays updated UI

Best Practices

✅ Keep Components focused on UI.

✅ Move business logic to Services.

✅ Keep API files responsible only for HTTP requests.

✅ Use React Query for server state.

✅ Validate before sending requests.

✅ Handle loading and error states.

✅ Use reusable hooks.

✅ Separate concerns between UI, logic, networking, and persistence.

Common Mistakes

❌ Calling Axios directly inside every component.

❌ Mixing UI code with business logic.

❌ Duplicating API calls.

❌ Keeping large amounts of state inside a single component.

❌ Ignoring loading and error states.

❌ Repeating validation logic in multiple places.

❌ Making components responsible for everything.

Chapter Summary

Understanding React data flow is more important than memorizing APIs or hooks.

Every enterprise React application is built around a layered architecture where each layer has one clear responsibility.
